# Slint no_std import design

## Goal

Import the minimal no_std-capable Slint dependency set into `external` using the existing gnrt workflow, so a separate no_std loader test app can compile simple Slint API usage.

The first validation target is `~/blueos-dev/kernel/loader/tests/inputs/no_std_app/src/main.rs`, limited to basic Slint types. Rendering, platform backends, windows, `.slint` files, and the `slint!` macro are out of scope for this import pass.

## Approach

Use the crates.io `slint` crate through the root `external/Cargo.toml` manifest, with default features disabled. This keeps the import aligned with the current gnrt workflow and lets Cargo/gnrt resolve the dependency graph instead of vendoring the upstream GitHub repository directly.

The intended dependency entry should use the crates.io version selected during implementation:

```toml
[dependencies.slint]
version = "..."
default-features = false
```

Prefer the current crates.io release accepted by Cargo unless dependency resolution requires pinning. No rendering or platform feature should be enabled unless basic type compilation proves it is required.

## Generated artifacts

Run the existing gnrt flow from `external`:

1. Update the root manifest and lockfile through `gnrt add` or equivalent Cargo manifest editing.
2. Run `gnrt vendor` to download Slint and its resolved dependencies into `vendor/`.
3. Run `gnrt gen` to generate `BUILD.gn` and `README.blueos` files.

If gnrt reports missing license files, build script outputs, generated sources, or extra inputs, add only the minimal crate-specific entries to `gnrt_config.toml` needed for generation to succeed.

## Validation

Validate the import in two layers:

1. In `external`, confirm Cargo resolution, vendoring, and GN generation complete successfully.
2. In the kernel no_std test app, add a small compile-only usage of basic Slint types such as `slint::SharedString`, `slint::Color`, or similarly lightweight public types.

The validation should not instantiate a window, renderer, backend, event loop, or component generated by `slint!`.

## Non-goals

- Do not vendor the full Slint GitHub repository directly.
- Do not import or wire platform/rendering backends.
- Do not validate `.slint` markup or the `slint!` macro in this pass.
- Do not refactor unrelated existing vendored crates or gnrt templates.

## Risks

The top-level `slint` crate may still pull in dependencies that are not no_std-friendly even with default features disabled. If that happens, first inspect the resolved feature graph and choose the smallest adjustment: disable an optional feature, add a gnrt config entry, or pin a compatible crates.io version. Switching to internal Slint crates should be treated as a fallback only if the public `slint` crate cannot support basic no_std API usage.
